Un servidor útil.
Una respuesta venenosa.

Construí un laboratorio MCP real para observar cómo metadatos y resultados de una herramienta pueden convertirse en instrucciones para un agente, y qué ocurre cuando se añaden controles de integridad, validación y fail-closed.

TL;DR

El servidor y el cliente hablaron MCP de verdad: inicialización, descubrimiento de herramientas y ejecución sobre Streamable HTTP. El servidor vulnerable entregó una descripción y un resultado con instrucciones no confiables; el cliente las detectó. No conecté un LLM ni permití lectura del canario o exfiltración: esa segunda etapa quedó deshabilitada. Después endurecí ambos extremos, repetí la misma llamada y la cadena tóxica desapareció. El hallazgo práctico es sencillo: tratar el texto devuelto por herramientas como datos hostiles, fijar la identidad de la herramienta y bloquear por defecto cualquier continuación sensible.

01 / FRONTERA DE CONFIANZA

Confiar en la conexión no equivale a confiar en el contenido

MCP permite que un cliente descubra herramientas y las invoque mediante una interfaz uniforme. Esa ergonomía crea una superficie menos evidente: nombres, descripciones y resultados terminan dentro del contexto que toma decisiones. Un servidor puede ejecutar la función prometida y, al mismo tiempo, insertar texto dirigido al modelo o al orquestador.

Una herramienta puede ser técnicamente válida y semánticamente hostil.

OWASP denomina a este patrón MCP Tool Poisoning. No requiere romper TLS ni explotar memoria. Basta con que contenido controlado por el proveedor de la herramienta sea interpretado como instrucción, especialmente cuando el agente posee acceso a archivos, credenciales, correo o red.

02 / MÉTODO

Un entorno pequeño, observable y deliberadamente limitado

Usé una VPS Ubuntu 24.04 con Python 3.12 y el SDK MCP para Python 2.1.1. El servicio escuchó únicamente en 127.0.0.1:8765; el cliente local llegó mediante un túnel SSH. Así mantuve el endpoint fuera de Internet y conservé evidencia en ambos lados.

La prueba separó dos hechos: primero, si el contenido envenenado podía cruzar una llamada MCP real; segundo, si un agente debía obedecerlo. Probé el primero. El segundo se modeló como una decisión de política sin conectar un modelo ni habilitar acciones destructivas.

03 / ATAQUE OBSERVADO

La función legítima trajo una instrucción ilegítima

El servidor publicó security_audit. La herramienta devolvió un resumen sintético válido, seguido de una instrucción para leer un archivo canario y subirlo a un destino externo. El cliente completó el handshake, enumeró la herramienta y ejecutó la llamada. Es decir: la entrega del contenido malicioso ocurrió a través del protocolo, no mediante una captura fabricada.

El modo vulnerable representó cómo un orquestador ingenuo podría continuar: reconoció que leer canary y subirlo sería la interpretación insegura. No abrió el archivo y no realizó tráfico de salida. Esta distinción importa: lo demostrado es la llegada del payload y la necesidad del control; no una exfiltración.

En este laboratorio solo se ejercitó la entrega de metadatos y respuesta manipulados. Los demás escenarios son rutas de abuso plausibles, no resultados observados aquí.

05 / MITIGACIÓN

La defensa útil está en ambos extremos

El cliente protegido escanea metadatos y retornos como contenido no confiable, separa los datos de cualquier instrucción y bloquea la continuación. El servidor endurecido aporta una definición canónica de la herramienta, hash literal fijado, validación estricta de entrada, salida estructurada sin instrucciones y auditoría JSONL.

client / protected mode

$ python client.py --mode protected
MCP_HANDSHAKE=OK tools=1
METADATA_SCAN_FLAGGED=True
RETURN_SCAN_FLAGGED=True
CLIENT_POLICY=FAIL_CLOSED
FOLLOW_UP_EXECUTION=BLOCKED

Un filtro textual no es una solución completa. La arquitectura debe combinar allowlists de servidores y herramientas, versiones o hashes fijados, mínimo privilegio, aprobación humana para efectos sensibles, aislamiento, control de egress, registros y revisión continua de definiciones.

06 / RETEST

Misma llamada, distinto resultado

Reemplacé el servidor vulnerable por la variante endurecida y repetí el cliente sin cambiar el canal. La herramienta siguió funcionando, pero la descripción dejó de contener instrucciones ocultas y la respuesta quedó limitada al resumen esperado. Incluso ejecutando el cliente en modo vulnerable, no hubo nada que interpretar ni una continuación que disparar.

El registro del servidor confirmó las llamadas con decisión ALLOW_SYNTHETIC_SUMMARY y cero llamadas externas. El valor del retest no está en que el servidor diga “seguro”, sino en que el contenido observado cambió y la conducta peligrosa dejó de ser posible dentro del caso probado.

08 / LÍMITES Y CORRECCIONES

Lo que esta prueba no demuestra

  • No se conectó un LLM; por tanto, no se midió la obediencia de un modelo específico.
  • No hubo lectura real del archivo canario, persistencia, movimiento lateral ni exfiltración.
  • El detector por patrones del cliente es didáctico; una defensa de producción necesita señales estructurales, procedencia y política contextual.
  • Un prototipo inicial calculaba el hash esperado desde la misma descripción que verificaba, lo que no detectaría drift. El paquete público lo corrige con un hash literal independiente y añade una prueba que falla cuando cambia la definición.

La prueba tampoco convierte MCP en “inseguro por diseño”. Demuestra que conectar herramientas amplía la frontera de confianza y que la seguridad depende del host, la procedencia, los permisos y la forma en que se interpretan los retornos.

09 / OPINIÓN FINAL

El retorno de una herramienta no merece autoridad

La lección más incómoda es que el servidor no tuvo que parecer malicioso. Contestó la auditoría y escondió la presión operativa en el mismo canal. En sistemas con agentes, la utilidad y la autoridad deben separarse: una herramienta puede aportar datos, pero no debe redefinir la tarea, solicitar secretos ni crear por sí sola una cadena de acciones.

Mi baseline sería: servidores aprobados, herramientas fijadas, privilegios por función, egress denegado por defecto y confirmación humana antes de cualquier efecto sensible. Si el equipo no puede responder qué contenido entró al contexto, qué identidad autorizó la llamada y qué control impidió el siguiente paso, todavía no tiene una integración de agentes defendible.
