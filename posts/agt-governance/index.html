Governing AI before
governing agents.

What Microsoft Agent Governance Toolkit can enforce at runtime, what remains outside its boundary, and why policy code is not a substitute for an AI governance program.

TL;DR

AGT produced useful enforcement when an operation traversed an instrumented wrapper or MCP server: deterministic decisions, pre-execution denial, limits, integrity checks, and correlatable evidence. It did not create a universal boundary around GitHub Copilot. More importantly, AGT is a runtime security component—not an AI governance program. An organization still needs ownership, inventory, risk classification, policy, lifecycle controls, assurance, and accountability before it can deploy enforcement responsibly.

01 / GOVERNANCE FOUNDATION

The work that must exist before AGT

A policy engine answers a narrow question: given this context and this proposed action, what verdict should the host enforce? It cannot decide which AI systems the organization accepts, who owns their risk, what data they may process, or when they must be retired. Those are governance decisions.

Before introducing AGT—or any agent runtime control—the organization needs a minimum control plane:

01Strategy & principlesApproved use cases, risk appetite, prohibited practices, and alignment with business objectives.
02Inventory & ownershipSystem register, model and agent inventory, accountable business owner, technical owner, and data owner.
03Risk classificationImpact tier, autonomy, data sensitivity, tool privileges, external dependencies, and human oversight.
04Policy & lifecycleIntake, assessment, testing, approval, change control, monitoring, incident response, and retirement.
05Assurance & accountabilityControl testing, evidence retention, exceptions, metrics, independent review, and named responsibility.
06Runtime enforcementAGT or equivalent policy enforcement points, approvals, limits, tool controls, and telemetry.

AGT belongs in the sixth layer and can provide evidence back to the fifth. It does not create the first five. Deploying it without them risks automating policies whose owner, scope, legal basis, and exception process are undefined.

02 / METHOD

The question was not “does a policy exist?”

Can the organization guarantee that every consequential action traverses the point where AGT decides—and that a deny prevents the effect?

This framing separates documentation from enforcement. A compliance mapping does not prove a host applies a verdict. A log is not a preventive control. A well-written rule has little value when the agent retains a parallel route to the same resource.

03 / TRUST BOUNDARY

The security model we observed

ACS acted as a policy decision point. The host assembled context, called the runtime, and enforced the result. That separation enables portable policy, but it also makes the host and integration path part of the trusted computing base.

04 / EMPIRICAL FINDINGS

Enforcement exists, but it is opt-in

Governed operations produced real ALLOW and DENY outcomes. A shell simulation was rejected before its implementation ran, with executed: false recorded in the correlated event. That is enforcement rather than observability.

agt-lab / runtime-controls

$ python test_remaining_runtime_controls.py
DEFAULT rm -rf: allowed=True
CONFIGURED rm -rf: allowed=False
CALL 3: allowed=False reason='Rate limit exceeded'
CUMULATIVE 110: allowed=False reason='Token budget exceeded (110/100)'

The default result matters: dangerous-command awareness was not a transparent sandbox. Explicit patterns changed the verdict, but text-based denylists admit variants. For command governance, structured operations and strict allowlists are more defensible than unrestricted shell interpretation.

Useful primitives still require engineering

Rate limiting, token budgets, maximum tool calls, concurrency, content hashes, supply-chain validation, human approval, and audit integrity worked when configured. Their value comes from composition. Their risk comes from assuming that composition happens automatically.

Integrity is not confidentiality

agt-lab / audit-integrity

$ python test_audit_integrity_runtime.py
BEFORE TAMPER: (True, 'Chain integrity verified')
AFTER TAMPER:  (False, 'Entry 0 hash mismatch')

The audit chain detected controlled mutation. A separate exercised path retained structured fictitious secrets in clear text. Events therefore need data minimization and key- and value-aware redaction before export to a SIEM.

AGT is not a sandbox

Path tests reached fixtures outside the workspace, and a native terminal path could act without producing ACS evidence. This is an architectural boundary. AGT does not replace operating-system permissions, process isolation, EDR, DLP, workload identity, secret brokering, or egress controls.

05 / SECURITY INTERPRETATION

Control coverage and residual risk

Policy enforcementEffective on mediated pathsMake routing mandatory

From a CISSP perspective, AGT fits defense in depth as an application-level policy enforcement point. By itself it does not satisfy complete mediation, least privilege, separation of duties, or data governance. When an alternate path exists, trust must move down to identity, endpoint, sandbox, network, and resource permissions.

06 / DECISION

Conditional go for a narrow pilot

A limited pilot is defensible only when tools are allowlisted and published through the governed path; terminal, filesystem, network, identity, and secrets have compensating controls; policy artifacts and fingerprints are protected; runtime failures fail closed; and evidence remains correlatable without retaining sensitive content.

CONDITIONAL GO

Use AGT for selected, measurable integrations after foundational AI governance exists. Do not present it as global Copilot protection or as a replacement for an AI management system.

07 / FINAL OPINION

Governance cannot be installed with pip

AGT is most compelling when it is treated as architecture rather than a promise of blanket protection. It can translate policy into consistent runtime decisions at intervention points an organization can actually impose. That is valuable—but it is downstream of governance.

The mature sequence is: know the AI systems, assign responsibility, classify risk, define policy, establish lifecycle controls, then automate selected decisions and collect evidence. Reversing that order creates technically sophisticated enforcement with no defensible governance context.

I would use AGT to govern selected MCP integrations. I would not use it to justify reducing sandboxing, IAM, DLP, EDR, network controls, or human accountability. The next useful test is complete mediation over one low-risk corporate use case, including bypass analysis and developer-impact measurement.
